## 1. Огляд

`oh-my-openagent` (npm-пакет, історично опублікований як `oh-my-opencode`) — центральний плагін оркестрації в екосистемі OpenCode. Назва наслідує конвенцію «oh-my-…», започатковану `oh-my-zsh`. Автор описує його так:

> «Якщо OpenCode — це Debian/Arch, то oh-my-openagent — це Ubuntu/[Omarchy](https://omarchy.org/).»

Він поєднує:

- **11+ спеціалізованих агентів** із моделлю оркестрації discipline-агентів
- **Систему скілів** із доменно-тюнізованими промптами та MCP-серверами на вимогу
- **54+ хуки життєвого циклу** (61 з увімкненим Team Mode)
- **5 вбудованих MCP-серверів** для поширених задач
- **Агента-планувальника** (Prometheus), який проводить інтерв'ю з користувачем перш ніж писати код
- **Само-референтний робочий цикл** (ralph-loop / ulw-loop), що тримає агента в задачі
- **Багатоагентний Team Mode** для паралельної скоординованої роботи
- **Редагування з хеш-прив'язкою** (hash-anchored edits) для надійніших змін, керованих моделлю

Філософія: «harness is the product». Більшість збоїв агентів — не провина моделі, а інструмент редагування, бюджет контексту, відсутність кроку планування. Плагін виправляє це на інфраструктурному рівні.

**Автор:** `code-yeongyu` (Sisyphus Labs). Плагін активно розробляється публічно — фічі та виправлення транслюються наживо в Discord проєкту.

## 2. Редакції

Пакет постачається у двох редакціях.

| Редакція | Середовище | Що отримуєте | Команда встановлення |
|---|---|---|---|
| **Ultimate** | OpenCode | Повний omo: 11 агентів, 54+ хуки, 5 MCP, всі slash-команди, Team Mode, ulw-loop, ultrawork, hashline edits | `bunx oh-my-openagent install` (TUI проведе вас) |
| **Light** | Codex CLI | Переносний піднабір для плагінної системи Codex: rules, comment-checker, LSP, ultrawork, ulw-loop, start-work-continuation, telemetry. Без оркестрації агентів, без `team_*` інструментів, без вбудованих MCP окрім LSP | `npx lazycodex-ai install` |

Цей документ описує лише редакцію **Ultimate** — саме її встановлює OpenCodeWizard.

### Назви пакетів і команд

Опублікований npm-пакет і CLI-бінарник усе ще називаються `oh-my-opencode` (подвійно публікується як `oh-my-openagent` під час перехідного перейменування). Усередині `opencode.json` шар сумісності надає перевагу запису плагіна `oh-my-openagent`; старі записи `oh-my-opencode` усе ще завантажуються з попередженням про deprecation. Працюють обидва варіанти — `bunx oh-my-openagent install` і старіший `bunx oh-my-opencode install`.

**Не** використовуйте `bunx omo` / `npx omo` — `omo` це інший, не пов'язаний npm-пакет від іншого автора, і менеджер пакетів може підставити саме його. Бінарний alias `omo` існує, але зарезервований для редакції Codex Light.

### Телеметрія

Анонімна телеметрія **увімкнена за замовчуванням**. Плагін надсилає одну подію `oh_my_openagent_daily_active` за UTC-день на машину, використовуючи SHA256-хешований ідентифікатор встановлення (сирий hostname ніколи не надсилається). Особисті профілі PostHog не створюються.

Щоб вимкнути — див. розділ конфігурації нижче.

## 3. Стан встановлення в цій системі

Перевірте, що зараз встановлено:

```bash
ls -d ~/.cache/opencode/packages/oh-my-openagent@latest
cat ~/.cache/opencode/packages/oh-my-openagent@latest/node_modules/oh-my-openagent/package.json \
  | python3 -c "import json,sys;p=json.load(sys.stdin);print('name:',p['name']);print('version:',p['version'])"
opencode --version
```

Версія, встановлена в цій системі, буде показана у виводі вище. На момент написання документа — **4.7.5**.

Плагін зареєстрований у `opencode.jsonc` користувача в масиві `plugin`:

```json
"plugin": [
  "oh-my-openagent",
  "opencode-mem",
  "@different-ai/opencode-browser",
  "@tarquinen/opencode-smart-title",
  "opencode-token-speed-plugin",
  "opencode-codebase-index"
]
```

Пресети `developer` і `standard` в OpenCodeWizard встановлюють `oh-my-openagent` за замовчуванням. Пресет `minimal` може його опускати.

### Користувацька конфігурація (де ви кастомізуєте плагін)

| Файл | Призначення |
|---|---|
| `~/.config/opencode/oh-my-openagent.json[c]` | Головний користувацький конфіг. Необов'язковий — дефолти вбудовані. |
| `~/.config/opencode/oh-my-opencode.json[c]` | Сумісна стара назва того самого файлу. Усе ще працює. |

Формат — **JSONC**: коментарі (`//`, `/* */`) і trailing commas дозволені. Схема — це об'єднання всіх `dist/config/schema/*.d.ts` у плагіні.

### Project-level overrides

OpenCode проходить дерево каталогів від `cwd` до `$HOME`, шукаючи:

```text
<dir>/.opencode/oh-my-openagent.json[c]
<dir>/.opencode/oh-my-opencode.json[c]   # сумісна стара назва
```

**Найближчий** до `cwd` файл виграє. Це дозволяє тримати project-specific overrides (наприклад, «завжди використовувати локальний llama.cpp для цього репо»), не засмічуючи глобальний конфіг.

### Інтеграція з головним конфігом OpenCode

Плагін реєструється у стандартному `opencode.json[c]` у масиві `plugin`. Жодної додаткової opencode-рівневої проводки не потрібно.

## 5. Вбудовані агенти

Плагін постачається з такими агентами. Імена та ролі взято з `dist/config/schema/agent-names.d.ts`.

### Вбудовані агенти з можливістю перевизначення

| Агент | Роль | Примітки |
|---|---|---|
| `sisyphus` | Головний оркестратор | Це «ви» — те, з чим ви розмовляєте. Усвідомлює режими, делегує субагентам, застосовує дисципліну Ultrawork. |
| `hephaestus` | Альтернативний оркестратор | Варіант, орієнтований на візуал/фронтенд. |
| `prometheus` | Планувальник | Проводить інтерв'ю з користувачем, визначає scope, будує верифікований план. Використовується `/start-work`. |
| `metis` | Передпланувальний консультант | Виявляє прихований намір, неоднозначності, точки збою AI в запиті *до* планування. |
| `momus` | Критик плану | Ворожий рецензент планів. Ловить прогалини, неоднозначності, відсутні кроки верифікації. |
| `oracle` | Read-only консультант | Високоінтелектуальне мислення для складного дебагу та архітектурних рішень. |
| `librarian` | Зовнішній reference grep | Пошук у віддалених репозиторіях, отримання офіційної документації, прикладів використання. |
| `explore` | Внутрішній code grep | Пошук у локальній кодовій базі. Дешевий і швидкий. |
| `multimodal-looker` | Інтерпретатор медіа | Читає PDF і зображення, коли сирий текстовий витяг недостатній. |
| `atlas` | (Зарезервований) | Доступний для кастомного підключення оркестрації. |
| `sisyphus-junior` | Фокусований виконавець | Той самий промпт, що й Sisyphus, але **без** оркестраційної обв'язки — виконується in-process, без делегування, без хуків. Використовується всередині контекстів субагентів. |

### Агенти OpenCode (експоновані плагіном, не винайдені ним)

| Агент | Примітки |
|---|---|
| `build` | Стандартний write/agent-режим OpenCode. |
| `plan` | Read-only режим планування OpenCode. |
| `OpenCode-Builder` | Аліас для зворотної сумісності. |

### Як перемкнути активного агента

У чаті OpenCode:

- Типовий top-level агент — `sisyphus`.
- Субагенти викликаються оркестратором через інструмент `Task(subagent_type=...)`. Зазвичай ви не викликаєте їх напряму.
- Щоб перевизначити типового агента для сесії, див. [Приклади конфігурації](#11-приклади-конфігурації).

## 6. Вбудовані скіли

Скіли — це зв'язки з:

- Доменно-тюнізовані системні інструкції
- Вбудовані MCP-сервери (на вимогу, обмежені скілом)
- Опціональні приклади робочих процесів

Вони завантажуються в контекст моделі при виклику відповідної slash-команди, або коли оркестратор виявляє, що тема відповідає. Скіли зберігаються в `packages/omo-codex/plugin/skills/`.

### Slash-скіли (викликаються через `/<назва>` у чаті)

| Slash-команда | Що робить |
|---|---|
| `/ulw-loop` | Вхід у цикл Ultrawork — агент працює, доки задача не виконана. |
| `/ulw-plan` | Планування в режимі Ultrawork, потім виконання. |
| `/start-work` | Викликає Prometheus для побудови верифікованого плану з цілі, потім виконує його. |
| `/init-deep` | Генерує ієрархічні файли `AGENTS.md` у проєкті для codebase-aware AI. |
| `/refactor` | Запускає скіл рефакторингу: LSP + AST-grep аналіз, codemap, TDD-верифікація. |
| `/review-work` | Рев'ю останніх змін на повноту та коректність. |
| `/remove-ai-slops` | Виявляє та прибирає code smells, згенеровані AI, з diff'а. |
| `/debugging` | Структурована методологія налагодження. |
| `/hyperplan` | 5 ворожих учасників категорій крос-критикують план, лід синтезує. |
| `/stop-continuation` | Зупиняє всі активні цикли (`ulw-loop`, `ralph-loop`, todos). |
| `/cancel-ralph` | Зупиняє лише Ralph-цикл. |
| `/handoff` | Створює контекстну вижимку для нової сесії. |

### Автозавантажувані скіли (без slash-команди)

| Скіл | Коли оркестратор його завантажує |
|---|---|
| `frontend-ui-ux` | Задача стосується UI/CSS/стилів/анімації. |
| `comment-checker` | Після написання коду сканує на оманливі або застарілі коментарі. |
| `lsp` | Коли потрібні LSP-усвідомлені правки чи рефакторинг. |
| `programming` | Загальні настанови з мов програмування. |
| `rules` | Завантажується один раз на початку сесії, містить постійні правила. |
| `lcx-report-bug` | Коли користувач повідомляє про баг. |

### Маніфест скілів (`dist/config/schema/agent-names.d.ts`)

Повний список скілів, які плагін заявляє як здатні завантажувати, згідно зі схемою:

```text
playwright, agent-browser, dev-browser, frontend-ui-ux,
git-master, review-work, remove-ai-slops, init-deep,
security-research, security-review, team-mode
```

Це **вбудовані** скіли, зареєстровані в OpenCode. Список вище — це зареєстрований у схемі набір. Фактичні скіли на диску в `packages/omo-codex/plugin/skills/` включають workflow-скіли (`ulw-loop`, `ulw-plan`, `start-work`, `debugging`, `refactor` тощо), які перераховані окремо.

## 7. Вбудовані MCP-сервери

Плагін постачається з MCP-серверами для поширених задач. Вони **інжектуються в рантаймі** — не з'являються в `opencode mcp list`, поки не завантажено скіл, який їх потребує.

| MCP | Призначення | Джерело |
|---|---|---|
| `websearch` | Пошук у вебі в реальному часі (на базі Exa) | `dist/config/schema/websearch.d.ts` |
| `context7` | Запит актуальної документації бібліотек | з README |
| `grep_app` | Пошук публічного коду GitHub (літеральні патерни, не ключові слова) | з README |
| (ще 2) | Зарезервовані для використання в скілах | |

Плюс усі MCP-сервери, які користувач зареєстрував у власному `opencode.jsonc` (наприклад, `fetch`, `puppeteer`, `postgres`, `codegraph`, `docs-mcp`, `lsp-mcp`, встановлені OpenCodeWizard).

### Skill-embedded MCP

Деякі скіли приносять власні MCP-сервери, які стартують **на вимогу**, коли скіл активний, і зупиняються, коли він завершений. Це зберігає контекстне вікно чистим — визначення інструментів MCP присутні лише поки відповідний скіл у scope.

## 8. Хуки життєвого циклу

## 9. Режими роботи та slash-команди

Плагін надає кілька «режимів», що змінюють поведінку агента. Вони викликаються як slash-команди в чаті.

### Каталог режимів

| Команда | Режим | Що відбувається |
|---|---|---|
| `/ulw-loop` (або просто `ultrawork` / `ulw`) | **Цикл Ultrawork** | Агент працює end-to-end без зупинки на підтвердження. Триває, поки задача верифікаційно не виконана. Це режим «здай це». |
| `/ulw-plan` | **Планування Ultrawork** | Та сама дисципліна, але спочатку продукує план, потім виконує. |
| `/ralph-loop` | **Ralph-цикл** | Само-референтний: агент продовжує викликати себе з блокнотом, доки не повідомить про завершення. Сильніша гарантія завершення ніж ulw-loop, повільніший. |
| `/hyperplan` | **Hyperplan** | 5 ворожих учасників категорій (різні ролі агентів) крос-критикують чорновий план. Лід синтезує. Найретельніший режим планування. |
| `/start-work` | **Робота під керівництвом Prometheus** | Викликає Prometheus для інтерв'ю з користувачем і побудови верифікованого плану, потім починає виконання. |
| `/init-deep` | **Ініціалізація проєкту** | Проходить кодовою базою, генерує ієрархічні файли `AGENTS.md`. Покращує майбутні сесії. |
| `/refactor` | **Прохід рефакторингу** | LSP + AST-grep + codemap + TDD-верифікаційний цикл. |
| `/review-work` | **Code review** | Рев'ю останніх змін. |
| `/remove-ai-slops` | **Прибирання слопу** | Виявляє та прибирає code smells від AI. |
| `/debugging` | **Структуроване налагодження** | Завантажує посилання на методологію. |
| `/handoff` | **Передача сесії** | Генерує контекстну вижимку для нової сесії. |
| `/stop-continuation` | **Зупинити все** | Скасовує всі активні цикли, todos і worktree. |
| `/cancel-ralph` | **Зупинити лише Ralph** | Скасовує Ralph-цикл, але залишає інші цикли активними. |

### Коли що використовувати

- **Ви точно знаєте, що хочете побудувати** → `/ulw-loop` або просто `ultrawork` / `ulw`
- **Є мета, але немає плану** → `/start-work` (Prometheus проведе інтерв'ю)
- **Є чорновий план і хочете його стрес-тестувати** → `/hyperplan`
- **Потрібна гарантія завершення, хоч скільки б часу це не зайняло** → `/ralph-loop`
- **Хочете прибрати перед комітом** → `/remove-ai-slops` + `/review-work`

### Як Sisyphus обирає режим автоматично

У типовому промпті Sisyphus певні фрази тригерять певні режими:

| Тригерна фраза в повідомленні | Авто-режим |
|---|---|
| «implement and finish», «do the whole thing», «ulw», «ultrawork», «ship it» | Ultrawork |
| «fix this whole thing», «look into» | Розслідування → планування, якщо scope незрозумілий |
| Довгі / багаторядкові цілі | Prometheus (`/start-work`) |

Це обробляється хуком `keyword-detector` та схемою `default-mode`.

## 12. Sisyphus — Оркестратор

Sisyphus — головний агент, з яким розмовляє користувач. Його промпт лежить у `dist/agents/sisyphus/`, з одним варіантом на підтримувану модель:

| Варіант | Використовується для |
|---|---|
| `claude-opus-4-7.d.ts` | Claude Opus 4.7 (та інші моделі Claude тієї ж родини) |
| `gpt-5-4.d.ts`, `gpt-5-5.d.ts` | Родина GPT-5 |
| `gemini.d.ts` | Родина Gemini |
| `kimi-k2-6.d.ts` | Kimi K2 |
| `default.d.ts` | Фолбек для нерозпізнаних моделей |

Варіант обирається автоматично на основі моделі, призначеної агенту `sisyphus`.

### Ключові обов'язки

Sisyphus:

1. **Розбирає намір користувача** (фаза планування, Phase 0 у промпті).
2. **Маршрутизує роботу** до спеціалізованих субагентів (делегування).
3. **Застосовує дисципліну Ultrawork** — продовжує працювати, доки задача верифікаційно не виконана.
4. **Верифікує результати** перед тим, як доповісти — використовує реальний інструмент для поверхні (браузер для UI, curl для HTTP, реальний бінарник для CLI).
5. **Залишається лаконічним** — без преамбул, без лестощів, без наративного статусу. Todos для відстеження, не балаканина.
6. **Кидає виклик користувачу**, коли дизайн хибний — пропонує альтернативи, ніколи не повчає.

### Ключові поведінкові правила (з промпта)

- **НІКОЛИ не починай імплементацію без явного запиту користувача** — спостереження, розслідування та відповіді на питання не зобов'язують до коду.
- **ДЕЛЕГУЙ, не працюй на самоті** — візуальна робота йде до `visual-engineering`, глибокий ресёрч — до паралельних агентів `explore`/`librarian`, архітектура — до `oracle`.
- **РЕАЛЬНЕ ВИКОРИСТАННЯ — це ворота верифікації** — пройдені тести недостатні. Агент мусить запустити бінарник, натиснути кнопки, звернутися до API.
- **ДОПОВІДАЙ ЧЕСНО** — про збої повідомляється з виводом, ніколи не замилюється.

### Чим Sisyphus **не** є

- Не одномодельний агент. Він обирає **категорії** (які відображаються на родини моделей) для кожної делегованої задачі, а не конкретні моделі.
- Не балакучий компаньйон. Використовує todos для відстеження, не наратив.
- Не всезнайко. Верифікує через інструменти, ніколи не припускає.

## 13. Prometheus — Планувальник

Prometheus — агент-планувальник, що викликається через `/start-work` та потік крос-критики `/hyperplan`.

### Що він робить

1. **Проводить інтерв'ю з користувачем** як справжній інженер: питає про scope, неоднозначності, обмеження, критерії успіху.
2. **Виявляє приховані вимоги**, які користувач не згадав (попередній прохід у стилі Metis).
3. **Будує ієрархічний план** із чіткими підцілями, кроками верифікації та ризиками.
4. **Записує план на диск** (хук `prometheus-md-only` примушує це — плани йдуть у `.md` файли, а не в стрічку чату).
5. **Передає на виконання** — коли план верифіковано, Sisyphus підхоплює його.

### Коли використовувати Prometheus

- Задача нетривіальна (більше ніж кілька правок файлів).
- Scope незрозумілий або існує кілька валідних підходів.
- Користувач може бути неправий у тому, чого він хоче.
- Зміна торкається багатьох модулів або має наскрізний характер.

### Коли Prometheus **не** потрібен

- Тривіальні зміни одного файлу.
- Чіткі, добре окреслені виправлення багів.
- Запити «просто зроби саме це».

Для тривіальної роботи звичайний Sisyphus швидший.

## 14. Інші помітні агенти

### `oracle` — Read-only консультант

Використовується для складного дебагу та архітектурних рішень, де ціна помилки висока. Oracle **read-only**: не редагує файли, не виконує команд із побічними ефектами. Лише читає, міркує, доповідає.

- Ціна: висока витрата токенів, повільний.
- Цінність: ловить ті тонкі баги взаємодії, що вилазять лише після 3 невдалих спроб виправлення.

### `metis` — Передпланування

Запускається до Prometheus. Виявляє прихований намір, неоднозначності та точки збою AI в запиті. 5-хвилинний прохід Metis може запобігти 2-годинній забудові в хибному напрямку.

### `momus` — Критик плану

Ворожий рецензент. Отримавши план, намагається його зламати. Ловить:

- Відсутні кроки верифікації
- Неоднозначні критерії приймання
- Нетестовані граничні випадки
- Неявні припущення

План, що пережив Momus, має набагато більше шансів на успіх.

### `explore` і `librarian` — Агенти пошуку

- `explore`: **внутрішній** code grep. Дешевий, швидкий, виконується in-process.
- `librarian`: **зовнішній** reference grep. Шукає на GitHub, отримує офіційну документацію, знаходить приклади використання через `gh` CLI + Context7 + Web Search. Повільніший, дорожчий.

Типовий потік згідно з промптом: `explore`/`librarian` (у фоні) + прямі інструменти → `oracle` за потребою.

### `sisyphus-junior` — Фокусований виконавець

Той самий промпт, що й Sisyphus, **мінус** оркестраційна обв'язка. Виконується всередині контекстів субагентів, де потрібна дисципліна, але не накладні витрати на делегування / хуки.

## 15. Team Mode

Team Mode (введено у v4.0) перетворює oh-my-openagent з «один агент із субагентами» на справжню багатоагентну систему.

Провідний агент оркеструє команду категорійно-спеціалізованих учасників, що працюють **паралельно** та спілкуються через спеціалізовані інструменти:

- `team_create` — створити команду
- `team_send_message` — надіслати повідомлення учаснику команди
- `team_task_create` — додати задачу до спільного беклога
- `team_status` — перевірити прогрес

Команда працює в tmux-розкладці з вікнами focus + grid — ви спостерігаєте, як кожен учасник працює одночасно.

Team Mode вмикається через конфіг-ключ `team_mode` і додає 7 хуків до типових 54.

## 16. Дисципліна Ultrawork

Ultrawork Manifesto (`docs/manifesto.md` у репо плагіна) — це проєктний документ. Ключові правила:

### Агент не зупиняється, доки задача не виконана

Підтвердження — це не «я гадаю, готово». Підтвердження — це **верифікаційно** готово:

- Правка файлу → `lsp_diagnostics` чисто
- Білд → exit code 0
- Тест → пройдено
- Делегування → результат верифіковано файл за файлом
- End-to-end делегування → агент використав артефакт через відповідний реальний інструмент (браузер для UI, curl для HTTP, сам бінарник для CLI)

### Без часткових виправлень

Якщо користувач передав end-to-end («ulw», «implement and finish», «do the whole thing», «make it work», «ship it»), делегування — це **мандат на виконання роботи**. Читання джерела — не валідація. Запуск реального інструмента з реальним користувацьким вводом — єдине валідне завершення.

### Чесна звітність

Тести впали → сказати так, з фактичним виводом. Білд не запускався → сказати «не запускався», не «має працювати». Тест, що падає, ніколи не видаляється заради зеленого білда.

### Інструменти — першокласні

Правильний інструмент обов'язковий:

- TUI/CLI робота → `interactive_bash` (tmux). Запустити бінарник у справжньому терміналі.
- Web/UI робота → справжній браузер через скіл `playwright`. Відрендерити зміну.
- HTTP API → `curl` до запущеного сервісу.
- Бібліотека/SDK → мінімальний драйвер-скрипт, що імпортує + виконує код.

«Має працювати» — не верифіковано. Верифіковано — коли користувач погодився б, що артефакт коректний.

## 17. Інтеграція з OpenCodeWizard

OpenCodeWizard встановлює та налаштовує `oh-my-openagent` у складі стандартного сетапу. Підключення знаходиться у трьох місцях:

### `config/plugins.conf`

```text
oh-my-openagent|Session management and advanced CLI commands
```

Це канонічний список плагінів. Візард читає його та додає обрані записи до `opencode.jsonc` користувача.

### `config/variables.conf` — визначення пресетів

Пресети `developer` і `standard` включають `oh-my-openagent`. Пресет `minimal` — ні. Щоб увімкнути oh-my-openagent у іншому пресеті, відредагуйте відповідний масив `PRESET_*_PLUGINS`.

### `OpenCodeWizard.sh` — `configure_opencode()`

Функція `configure_opencode()` будує JSONC для `opencode.jsonc`. Вона записує масив `plugin`, об'єкт `mcp`, масив `instructions` і (опціонально) блок `provider`. Вона **не** генерує окремий `oh-my-openagent.json[c]` — плагін умикається повністю через стандартний масив `plugin`.

### `config/system_info.md.tpl` — системний промпт AI

Шаблон може посилатися на можливості oh-my-openagent у системному промпті, який він генерує. Стандартний шаблон згадує спільний термінал, правило git-операцій та екосистему OpenCode — усе це інтегрується з хуками плагіна.

### Перевірка інтеграції

Після запуску візарда `~/.config/opencode/opencode.jsonc` користувача має містити:

```jsonc
{
  "plugin": [
    "oh-my-openagent",
    // … інші плагіни …
  ]
}
```

Запустіть opencode. У першому чаті має з'явитися ідентичність Sisyphus. Якщо ви бачите звичайну поведінку OpenCode — плагін не завантажується; перевірте логи opencode.

## 18. Видалення

README плагіна дає єдину чисту процедуру. Щоб видалити `oh-my-openagent` із цієї системи:

1. **Приберіть зі списку плагінів.** Відредагуйте `~/.config/opencode/opencode.jsonc` і видаліть `"oh-my-openagent"` з масиву `plugin`. Опціонально також приберіть інші плагіни, які вам більше не потрібні.

2. **(Опціонально) Видаліть користувацький конфіг.** Якщо ви створювали `~/.config/opencode/oh-my-openagent.json[c]` або project-level overrides — видаліть їх.

3. **(Опціонально) Очистіть кеш.** Плагін живе в `~/.cache/opencode/packages/oh-my-openagent@latest/`. Його видалення безпечне — opencode перезавантажить, якщо плагін знову увімкнено.

4. **Перезапустіть opencode.** Перезавантажте, щоб підхопити зміни.

5. **(Опціонально) Вимкніть телеметрію на тих встановленнях, що залишилися.** Поставте `"experimental": { "telemetry": { "enabled": false } }` у вашому користувацькому конфігу.

Глобальної команди «uninstall» у самому плагіні немає. Вище — канонічна процедура.

## 19. Усунення несправностей

### Плагін увімкнено, але Sisyphus не є активним агентом

Перевірте `opencode.jsonc` на ключ `agent`, що перевизначає типового. Sisyphus — типовий top-level агент, коли `oh-my-openagent` завантажений, але override користувацького рівня може це змінити.

```jsonc
// Примусово Sisyphus як типового
{
  "agent": "sisyphus"
}
```

### Slash-команди не працюють

Slash-команди реєструються плагіном. Якщо `/ulw-loop` нерозпізнаний — плагін не завантажений. Перевірте:

```bash
ls -d ~/.cache/opencode/packages/oh-my-openagent@latest
grep '"oh-my-openagent"' ~/.config/opencode/opencode.jsonc
```

Якщо пакета немає — перевстановіть. Якщо запису немає в `plugin` — додайте.

### Субагенти не викликаються

Типово Sisyphus делегує через інструмент `Task`. Якщо ваша модель не підтримує коректно tool use, делегування пропускається. Плагін намагається відкотитися до in-process виконання через `sisyphus-junior`, але дисципліна слабша.

Перевірте новою сесією `opencode` із чітко делегованою задачею («знайди реалізацію auth у цій кодовій базі»). Якщо Sisyphus не викликає `explore`/`librarian` — ваша модель, можливо, не маршрутизує виклики інструментів коректно.

### Вимкнення телеметрії не поважається

Вимкнення — на одне встановлення. Плагін використовує SHA256-хешований installation ID — очищення кешу примушує новий ID і скидає вимкнення. Повторіть конфіг після очищення.

### Скіл повідомляє «not found»

Деякі скіли платформо-специфічні. `playwright` потребує Chromium-бінарник. `agent-browser` і `dev-browser` мають власні кроки налаштування. Див. `SKILL.md` скіла щодо передумов.

### Моделі в `oh-my-openagent.json[c]` мовчки ігноруються

Система перевизначення моделей плагіна має відому примхливість маршрутизації простору імен у старіших версіях opencode (див. трекер проблем `oh-my-openagent` для `@ai-sdk/openai-compatible`). Для локальних моделей, що використовують OpenAI-сумісний SDK, `baseURL` і `apiKey` можуть не пересилатися коректно в SDK. Обхідні шляхи:

- Зафіксуйте свіжу версію opencode.
- Використовуйте поле `model` per-agent у стандартному блоці `provider` файлу `opencode.jsonc`.
