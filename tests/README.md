# Automated Testing in OpenCodeWizard

*Read this in other languages: [Українська (README.uk.md)](README.uk.md)*

This directory contains the testing framework for verifying the functionality of the OpenCodeWizard automation scripts in various environments.

Testing is performed automatically using Docker containers, which allows for isolating system package installations and verifying script behavior without affecting your main host operating system.

---

## Directory Structure

- **`run_tests.sh`** — The main test runner script. It orchestrates starting containers, installing base prerequisites, cloning the repository, running the installation script in silent/non-interactive mode, and running assertions.
- **`verify_install.sh`** — The verification script executed inside each container. It runs assertions to verify that WezTerm, OpenCode CLI, and plugins are correctly installed, and that configuration files are valid and contain proper values.
- **`README.md`** — This documentation file (English).
- **`README.uk.md`** — The Ukrainian version of this documentation.

---

## Target Environments

Automated tests are executed in containers for the following Linux distributions:

1. **Ubuntu** (`ubuntu:24.04`) — Tests `apt-get` integration, `update-alternatives` registration, and XDG terminal setup.
2. **Fedora** (`fedora:40`) — Tests `dnf` integration.
3. **Arch Linux** (`archlinux:latest`) — Tests `pacman` integration. Arch is a rolling release, so it stays on `latest`.
4. **PowerShell Core** (`mcr.microsoft.com/powershell:latest`) — Verifies the syntax of the Windows script `OpenCodeWizard.ps1` using the PowerShell AST parser.

> **Pinned tags** (`ubuntu:24.04`, `fedora:40`) keep builds reproducible — Docker caches layers aggressively on immutable tags, cutting test time **2–4×** compared to `:latest` (which always re-pulls).

## Pre-built Docker Images

Tests run against pre-built images (`ocw-test:ubuntu`, `ocw-test:fedora`, `ocw-test:arch`) defined in `tests/Dockerfile.test`. The image is built automatically the first time a test runs in a fresh Docker daemon and reused on subsequent runs. This avoids re-running `apt-get install` / `dnf install` / `pacman -S` for every test invocation.

The Dockerfile is universal — it uses `ARG DISTRO` to pick the base image and dispatches to the right package manager (`apt-get` / `dnf` / `pacman`) inside the `RUN` layer.

### Build test images manually

```bash
make build-test-images
```

This builds all three images. You can also build a single image:

```bash
docker build --build-arg DISTRO=ubuntu:24.04 -t ocw-test:ubuntu -f tests/Dockerfile.test .
```

## How It Works

Testing in Docker is fully automated and runs without user interaction using the silent/non-interactive mode:

1. `run_tests.sh` resolves the distro short name to a pinned base image (`ubuntu` → `ubuntu:24.04`, etc.).
2. If the pre-built image `ocw-test:<distro>` is missing, it is built from `tests/Dockerfile.test` with `apt-get`/`dnf`/`pacman` installing the prerequisites once.
3. The pre-built container starts and mounts the workspace at `/app`.
4. `./OpenCodeWizard.sh --silent` runs non-interactively, applying all default choices.
5. `./tests/verify_install.sh` runs assertions:
   - `opencode` is in the PATH and returns a valid version number.
   - Configuration files (`wezterm.lua` and `opencode.jsonc`) exist.
   - The plugin entry for `"oh-my-opencode"` is correct (verifies that `"oh-my-openagent"` is not present).
   - Shell exports are correctly written to `~/.bashrc` (`TERMINAL=wezterm` + `OPENCODE_AGENTS_SWITCH_SINGLE_MODEL=true`).
   - The desktop launcher file exists, is executable, and points to the correct target.
   - **`wezterm` binary check is skipped** in containers — GUI packages cannot be installed headless. The WezTerm **config file** check still runs (it is generated by `configure_wezterm()` regardless of binary install).

## Running Tests Locally

To run the test suite, you need to have **Docker** installed and running on your host machine.

1. Open your terminal in the root directory of the project.
2. Run a single distro test:

   ```bash
   ./tests/run_tests.sh ubuntu
   ./tests/run_tests.sh fedora
   ./tests/run_tests.sh arch
   ./tests/run_tests.sh powershell
   ```

3. Or run the full suite (all distros × all presets):

   ```bash
   ./tests/run_tests.sh
   ```

### Using `make` shortcuts

```bash
make build-test-images   # Build all 3 pre-built images
make test-ubuntu         # Run Ubuntu test only
make test-fedora         # Run Fedora test only
make test-arch           # Run Arch test only
make test-powershell     # Run PowerShell syntax check
make test                # Build images + run full suite
```

The script will run all test suites sequentially and output a final summary. If all tests pass, it exits with code `0`. If any suite fails, it exits with a non-zero code, making it suitable for CI/CD workflows.

### Parallel execution in pre-push hook

The `.githooks/pre-push` hook runs the four Docker-based tests (`ubuntu`, `fedora`, `arch`, `powershell`) **in parallel** via bash background `&` + `wait`, then aggregates pass/fail into `/tmp/ocw-test-results`. A failure of any single test aborts the push. On a 4-core host the wall-clock time of the CI step is roughly **the slowest single test**, not the sum.

### Test Current State (Local changes)

By default, the script copies all local modifications (including uncommitted files) to run tests against your active working directory:

```bash
./tests/run_tests.sh
```

### Test GitHub Repository State (Post-Push)

To test the exact state of the repository cloned directly from GitHub (simulating post-push behavior), run the separate GitHub test script:

```bash
./tests/run_tests_github.sh
```
