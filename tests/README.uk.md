# Автоматичне тестування в OpenCodeWizard

*Читати іншими мовами: [English (README.md)](README.md)*

Цей каталог містить тестовий фреймворк для перевірки працездатності скриптів автоматизації OpenCodeWizard у різних середовищах.

Тестування виконується автоматично за допомогою Docker-контейнерів, що дозволяє ізолювати встановлення системних пакетів та перевіряти поведінку скрипта без впливу на вашу основну операційну систему.

---

## Структура каталогу

- **`run_tests.sh`** — головний скрипт запуску тестів. Він керує створенням контейнерів, встановленням залежностей, запуском інсталятора в німому/неінтерактивному режимі та виконанням перевірок.
- **`verify_install.sh`** — перевірочний скрипт, який запускається всередині кожного контейнера. Він виконує перевірки (assertions) для підтвердження того, що WezTerm, OpenCode CLI та плагіни встановлені правильно, а конфігураційні файли є валідними та містять правильні параметри.
- **`README.md`** — англомовна версія цього посібника.
- **`README.uk.md`** — україномовна версія цього посібника (цей файл).

---

## Цільові середовища

Автоматичні тести виконуються в контейнерах таких дистрибутивів Linux:

1. **Ubuntu** (`ubuntu:24.04`) — тестує інтеграцію `apt-get`, реєстрацію в `update-alternatives` та налаштування терміналу XDG.
2. **Fedora** (`fedora:40`) — тестує інтеграцію `dnf`.
3. **Arch Linux** (`archlinux:latest`) — тестує інтеграцію `pacman`. Arch — rolling release, тому залишається на `latest`.
4. **PowerShell Core** (`mcr.microsoft.com/powershell:latest`) — перевіряє синтаксичну валідність Windows-скрипта `OpenCodeWizard.ps1` за допомогою AST-парсеру PowerShell.

> **Закріплені теги** (`ubuntu:24.04`, `fedora:40`) забезпечують відтворюваність збірок — Docker агресивно кешує шари для незмінних тегів, що прискорює тести у **2–4 рази** порівняно з `:latest` (який завжди перетягується).

## Попередньо зібрані Docker-образи

Тести запускаються на попередньо зібраних образах (`ocw-test:ubuntu`, `ocw-test:fedora`, `ocw-test:arch`), описаних у `tests/Dockerfile.test`. Образ збирається автоматично при першому запуску тесту в "свіжому" Docker-демоні та використовується повторно в наступних запусках. Це усуває повторний `apt-get install` / `dnf install` / `pacman -S` під час кожного виклику тесту.

Dockerfile є універсальним — він використовує `ARG DISTRO` для вибору базового образу та перемикає на потрібний менеджер пакунків (`apt-get` / `dnf` / `pacman`) всередині шару `RUN`.

### Зібрати тестові образи вручну

```bash
make build-test-images
```

Ця команда збирає всі три образи. Також можна зібрати окремий образ:

```bash
docker build --build-arg DISTRO=ubuntu:24.04 -t ocw-test:ubuntu -f tests/Dockerfile.test .
```

## Як це працює

Тестування в Docker повністю автоматизовано і виконується без участі користувача завдяки німому (неінтерактивному) режиму:

1. `run_tests.sh` зіставляє коротке ім'я дистрибутива із закріпленим базовим образом (`ubuntu` → `ubuntu:24.04` тощо).
2. Якщо попередньо зібраний образ `ocw-test:<distro>` відсутній, він збирається з `tests/Dockerfile.test`, де `apt-get` / `dnf` / `pacman` встановлюють залежності один раз.
3. Попередньо зібраний контейнер стартує та монтує робочу директорію у `/app`.
4. `./OpenCodeWizard.sh --silent` виконується неінтерактивно, приймаючи всі значення за замовчуванням.
5. `./tests/verify_install.sh` виконує перевірки (assertions):
   - `opencode` присутній у PATH та повертає коректну версію.
   - Конфігураційні файли (`wezterm.lua` та `opencode.jsonc`) існують.
   - Правильність імені плагіна `"oh-my-opencode"` (перевіряє відсутність застарілого запису `"oh-my-openagent"`).
   - Наявність експорту змінних у `~/.bashrc` (`TERMINAL=wezterm` + `OPENCODE_AGENTS_SWITCH_SINGLE_MODEL=true`).
   - Створення ярлика запуску на робочому столі, його права на виконання та коректність команди запуску.
   - **Перевірку бінарника `wezterm` пропущено** в контейнерах — GUI-пакети неможливо встановити в headless-середовищі. Перевірка **конфігураційного файлу** WezTerm все одно виконується (він генерується `configure_wezterm()` незалежно від встановлення бінарника).

## Як запустити тести локально

Для запуску тестів вам знадобиться встановлений та запущений **Docker**.

1. Відкрийте термінал у кореневій папці проекту.
2. Запустіть тест для конкретного дистрибутива:

   ```bash
   ./tests/run_tests.sh ubuntu
   ./tests/run_tests.sh fedora
   ./tests/run_tests.sh arch
   ./tests/run_tests.sh powershell
   ```

3. Або запустіть повний набір тестів (усі дистрибутиви × усі пресети):

   ```bash
   ./tests/run_tests.sh
   ```

### Використання скорочень `make`

```bash
make build-test-images   # Зібрати всі 3 попередньо зібраних образи
make test-ubuntu         # Запустити лише Ubuntu-тест
make test-fedora         # Запустити лише Fedora-тест
make test-arch           # Запустити лише Arch-тест
make test-powershell     # Запустити перевірку синтаксису PowerShell
make test                # Зібрати образи + запустити повний набір
```

Скрипт по черзі виконає всі перевірки та виведе підсумковий звіт. Якщо всі тести пройдено успішно, він завершиться з кодом `0`. У разі помилки в будь-якому контейнері — поверне ненульовий код помилки, що робить його придатним для використання в CI/CD (наприклад, GitHub Actions).

### Паралельне виконання в pre-push hook

Хук `.githooks/pre-push` запускає чотири Docker-тести (`ubuntu`, `fedora`, `arch`, `powershell`) **паралельно** через bash-фоновий `&` + `wait`, а потім агрегує pass/fail у `/tmp/ocw-test-results`. Збій будь-якого одного тесту перериває push. На 4-ядерному хості час CI-кроку приблизно відповідає **найповільнішому одиночному тесту**, а не їх сумі.

### Тестування поточного стану (Локальні зміни)

За замовчуванням скрипт копіює всі локальні зміни (включаючи незакомічені файли) для запуску тестів у вашій поточній робочій директорії:

```bash
./tests/run_tests.sh
```

### Тестування стану репозиторію на GitHub (Post-Push)

Щоб протестувати точний стан репозиторію, клонованого безпосередньо з GitHub (імітуючи поведінку після пушу), запустіть окремий скрипт тестування GitHub:

```bash
./tests/run_tests_github.sh
```
